# Milestone-controlled implementation plan

Only milestone 0 is authorized now. All application milestones 1–12 are unstarted. Future implementation requires explicit milestone approval after teaching/reference/design discussion; Codex may then generate code/tests within that scope. Names below describe responsibilities, not code already written.

## M0 — Research, architecture and documentation

**Objective:** define the original Java system and all twelve PS scenarios, document design alternatives, and publish honest planning docs. **Concepts:** financial versus operation state, external uncertainty, aggregate boundaries. **Design/tasks:** requirements/domain/API/processor design, ADRs, scenario matrix and mentoring workflow. **Tests/review:** links, citations, Mermaid, consistency, docs-only/secret scan and remote repository verification. **Failures:** unsupported guarantee, unsupported stack pin, lost repository material. **Done:** explicit design rationale and gaps, meaningful plans and verified publication; no application code. **Interview:** defend clean-room scope and external atomicity gap. **Dependencies:** owner master plan; repository deletion requires an explicit owner instruction.

## M1 — Spring Boot, PostgreSQL and REST foundations

**Objective:** owner-approved smallest persistence/API slice, not payment effects yet. **Learn:** Java 21 values/interfaces/errors, Maven BOM, DI/MVC, DTO validation, JPA transaction/flush, Flyway and DB constraints. **Design:** health/resource boundary, merchant scope, error DTO and one persisted nonfinancial resource. **Tasks:** verify and pin compatible Spring Boot 4.x, managed JUnit 6/Jupiter and integration-library patches before build generation; write minimal build/schema/API and safe logs. **Tests:** actual PostgreSQL/Testcontainers commit/rollback/restart, validation, actor scope, error mapping. **Faults:** DB unavailable, duplicate reference and process restart. **Done:** resource persists and errors are honest; no false durable acceptance. **Tradeoff:** ORM convenience versus explicit SQL and managed defaults versus justified overrides. **Interview:** when does a DB constraint fail; why not expose entities? **Dependencies:** approved M0 design and explicit M1 approval.

## M2 — Authorization lifecycle and state machine

**Objective:** accepted authorization/payment/operation/inquiry vertical slice with a minimal local processor port. **Learn:** minor units, authorization/capture distinction, confirmed versus execution state, transaction boundaries. **Design:** Money, policy, payment/operation/attempt records, 202 resource contract; external IO outside DB. **Tasks:** owner/Codex implements allowed transitions, atomic acceptance, current-state reads, deterministic approve/decline fake and bounded outcome application. **Tests:** legal/illegal transitions, overflow/currency, rollback, confirmed decline versus timeout placeholder. **Faults:** lose HTTP acceptance response; fail final result commit. **Done:** stable persisted IDs and honest state, clearly not full recovery yet. **Tradeoff:** durable asynchronous acceptance versus synchronous waiting. **Interview:** why is an accepted request not a successful authorization? **Dependencies:** M1 approval/completion; full adapter/routing comes M4, uncertainty M5.

## M3 — Idempotency and concurrent commands

**Objective:** prove PS-01 with real concurrent connections/processes. **Learn:** unique constraints, semantic hashes, transaction abort, lock scope and linearization. **Design:** scoped idempotency record, business-reference guard, original acceptance replay and changed-body conflict. **Tasks:** implement atomic winner insertion, fresh-transaction loser lookup, retention policy and bounded wait. **Tests:** 50 synchronized identical requests; changed currency/amount, different merchants, winner rollback, commit-before-response crash and two instances. **Faults:** barrier between lookup/insert, lost response, constraint exception. **Done:** one logical payment/operation and consistent replay identity, no duplicate fake effect in declared scenario. **Tradeoff:** cache versus durable key, retaining snapshot versus rebuilding response. **Interview:** idempotency versus at-most-once transport/business duplicates? **Dependencies:** M2; PS-01 foundation for all later commands.

## M4 — Processor adapters and routing

**Objective:** two independently stateful simulated processors and recorded deterministic routing. **Learn:** ports/adapters, capability/error mapping, intent/attempt identity, provider state. **Design:** common per-flow contracts, provider key, route/rule snapshot, priority and currency/capability eligibility. **Tasks:** implement A/B with different request/status shapes, shared contract suite, sticky origin, minimal healthy-route configuration. **Tests:** normalization, unsupported capabilities, no wrong-currency route, route history, source amount mismatch. **Faults:** known pre-dispatch outage and malformed provider response. **Done:** both adapters process supported slice independently; selection is explainable; no unsafe automatic fallback. **Tradeoff:** deterministic priority versus dynamic routing; defer configurable routing languages and complex retry rule engines until needed. **Interview:** which provider semantics cannot be normalized away? **Dependencies:** M3; PS-03 advanced outage logic at M5.

## M5 — Timeouts, unknown outcomes and safe fallback

**Objective:** PS-02/03/06 with durable inquiry/recovery foundations. **Learn:** remote atomicity gap, leases/fences, deadlines/backoff/jitter, circuit breaker/bulkhead. **Design:** dispatch marker and attempt record before IO, UNKNOWN state, stable provider key, due-job scanner and classified retry matrix. **Tasks:** write short claims/fenced finalization/inquiry schedules; add provider-specific Resilience4j boundaries only where justified; retain reservations and no uncertain cross-provider retry. **Tests:** effect→lost response, inquiry absent/restored, stale worker, 429/500-after-effect, healthy B under slow A. **Faults:** kill every provider/local commit window; exhaust retries. **Done:** one remote effect or explicit unresolved state, bounded work, safe routing only for proven-undispatched operations. **Tradeoff:** resubmission versus inquiry/escalation. **Interview:** why doesn't lease expiry stop a provider call? **Dependencies:** M4; full worker/webhook corpus M8.

## M6 — Capture, void, refund and applicable reversal

**Objective:** financial lifecycle and PS-04/05; human-commerce adapter can later use it. **Learn:** row locks/version conflicts, reservations, legal transitions, provider-specific reversal. **Design:** single active operation per payment, conditional bounded totals, linked original provider chain. **Tasks:** implement full capture, uncaptured cancel/void, full then partial refunds, inquiry/apply-once; reversal only declared capability with explicit unknown handling. **Tests:** capture/capture, capture/cancel, refund/refund barriers; unknown reservation, late/duplicate result, over/negative/overflow/currency and unsupported reversal. **Faults:** lock wait/deadlock, crash after effect, delayed refund confirmation. **Done:** all invariants hold; no optimistic client success or refund release based on silence. **Tradeoff:** serialized operations versus future parallel reservation-aware refunds. **Interview:** what if cancellation/refund itself times out? **Dependencies:** M5; future tests preserve all PS scenarios.

## M7 — Transactional outbox, Kafka and consumers

**Objective:** PS-08/09 and replayable committed facts. **Learn:** dual write, at-least-once, partitions/offsets/rebalance and dedup scope. **Design:** atomic audit/outbox with stable ID/sequence, polling relay, consumer inbox+effect transaction; single publisher first. **Tasks:** implement outbox before broker, then Kafka adapter/topic key/schema handling and controlled quarantine/replay. **Tests:** rollback means no event, publish-then-marker crash duplicates identity, consumer crash after DB/before offset, reordered versions and unknown schema. **Faults:** stop broker, lose ack, reset isolated offsets, poison event. **Done:** no lost committed intent, one local effect on replay, bounded visible backlog; financial commands work during bounded broker outage. **Tradeoff:** polling versus CDC; Kafka versus simpler DB work. **Interview:** scope exactly-once claims precisely. **Dependencies:** M6; commerce contract designed M0, consumer later.

## M8 — Webhooks and durable recovery

**Objective:** PS-07/10 with complete source/recovery corpus. **Learn:** source signature/raw bytes, idempotent observation, event versus effect identity, stale owners and fencing. **Design:** bounded verified inbox, authoritative inquiry on conflicting/gapped data, robust claim/reclaim/job generations. **Tasks:** implement source-specific verification and merge, receipt-before-2xx, sweeper, attempt/unknown aging and operator investigation views. **Tests:** invalid signature, duplicate/reversed/new-ID same effect, stale pending-after-success, kill/pause old owner, DB connection loss and late completion. **Faults:** stop worker mid-job, release old worker after takeover, inquiry outage, repeated callbacks. **Done:** one effect and honest final/unknown state, no stale regression; accepted work accounted for. **Tradeoff:** reject/quarantine versus bounded source refresh; no timestamp-only order. **Interview:** why test pause and kill separately? **Dependencies:** M7, recovery foundation M5.

## M9 — Settlement and reconciliation

**Objective:** PS-11 with original synthetic format and deterministic exceptions. **Learn:** capture/settlement/payout separation, fee/net signs, completeness, calendars and exact matching. **Design:** staged batch/row identities, versioned matcher, resume checkpoints, stable exception occurrence. **Tasks:** write bounded parser, validation, close/grace policy, exact match and discrepancy/duplicate/missing classification, correction revisions/outbox. **Tests:** duplicate/import retry, bad fee/net, wrong currency/reference/kind, incomplete window, late correction, ambiguous match. **Faults:** crash mid-import/match, omit file segment, advance controlled clock past grace. **Done:** rerun idempotent, source evidence attached, no false absence on incomplete input or rewritten payment truth. **Tradeoff:** exact versus heuristic candidate matching; bank three-way recon deferred. **Interview:** what proves a missing settlement? **Dependencies:** M8; public recon docs are not assumed open-source engine code.

## M10 — Performance engineering and observability

**Objective:** PS-12 and measured bottleneck diagnosis. **Learn:** arrival rate, p95/p99, saturation, coordinated omission, query plans/indexes/pools and low-cardinality telemetry. **Design:** k6/fault simulator scenarios, hardware/config/seed manifest, stop bounds and correctness-after-drain checks. **Tasks:** implement tests only after approval; baseline small then explore 100/500/1,000 RPS if feasible; instrument traces/metrics/dashboards and improve one measured bottleneck. **Tests:** hot key/merchant, replay storms, slow provider, broker/DB pressure and bounded admission. **Faults:** pool starvation and backlog growth. **Done:** actual offered/accepted/rejected/completed/unknown/effect counts, tail latency and limits published; no Stripe/LLM load traffic or invented results. **Tradeoff:** throughput/latency/correctness; pool size versus contention. **Interview:** explain observed bottleneck and proposed change with evidence. **Dependencies:** M9 and correctness corpus passes.

## M11 — Stripe sandbox and separately approved deployment

**Objective:** supported low-volume integration and, only if separately approved, runnable deployment. **Learn:** test/live keys, Stripe object/version/manual capture/refunds/webhooks, sandbox limitations, ECS/RDS/secrets/backup/cost boundaries. **Design:** third adapter and source-specific mapping; local/sandbox/production configuration cannot mix; no real funds. **Tasks:** write integration after sandbox/API authorization, verify signatures/current object inquiry; deployment/CI/config only within explicit approval, not assumed by prior documentation publication. **Tests:** documented sandbox cases, duplicate callbacks, denied live mode, unavailable source; deployment checks separate. **Faults:** drop local response, revoke test credential, failed health/readiness. **Done:** source provenance and limits recorded; no production-scale/bank settlement claim; cloud portion can remain deferred without inventing completion. **Tradeoff:** integration realism versus simulator control. **Interview:** which facts were Stripe versus injected? **Dependencies:** M10 for performance claims, financial correctness earlier.

## M12 — Commerce integration contract verification

**Objective:** verify the M0-designed contract against the implemented commerce client. **Learn:** separate authority/order/payment states, saga compensation, schema evolution and independent demos. **Design:** versioned commands/events and shared fixtures; scoped client and original-linked financial actions. **Tasks:** implement integration adapter/contract fixtures after approval; document happy/lost-response/dispense-failure demos and actual limits. **Tests:** AC-01/05/07/08 mapping, denied scope/hash/amount, duplicate/reordered facts, source unavailable and both independent modes. **Faults:** stop one system, replay event, crash compensation worker. **Done:** both run independently; integrated report reflects real source state; no model-owned financial decisions or duplicate effects. **Tradeoff:** protocol adapters deferred until interoperability demand. **Interview:** strongest demonstrated guarantee and its assumptions? **Dependencies:** Java M6/M8 plus commerce M6/M8/M9; M12 does not defer contract design until then.
